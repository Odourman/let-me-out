## 2. FYND A – kommandotransporten har ingen programmatisk inmatningskvittens

**Källbelagt:** [G5AL `send()` rad 140–148](https://github.com/Odourman/let-me-out/blob/f16e1e4ac3736e3d6bb1bc0b959b0213e28f6431/rom/g5al_f9_method_2026-11-18/run_g5al_f9.sh#L140-L148) testar **bara fönstertitel**, loggar den AVSEDDA kommandosträngen till `commands_sent.txt`, utför `xdotool type --window ... --delay 30`, separat `xdotool key ... Return` och `sleep 0.40`. **Inga kontroller visar att en färdig Stella-prompt verkligen hunnit acceptera eller exekvera strängen före nästa kommando.** [`PromptWidget::handleText`](https://github.com/stella-emu/stella/blob/6.7.1/src/debugger/gui/PromptWidget.cxx#L136-L149) appenderar tecken till samma rads redigeringsbuffert. [`handleKeyDown`](https://github.com/stella-emu/stella/blob/6.7.1/src/debugger/gui/PromptWidget.cxx#L153-L175) aktiverar `execute` på EndEdit/Enter. [`PromptWidget::execute`](https://github.com/stella-emu/stella/blob/6.7.1/src/debugger/gui/PromptWidget.cxx#L670-L703) kör sedan sträng till parsern. **`commands_sent.txt` är extern sändlista, inte verklig mottagarkvittens.**

**Faktisk bevisning:** G5AL run 1 sparade bokstavligen `> print pcprint _fCount` och Stellas svar `too many arguments`. Det är en **verkligt observerad inmatningskollision** och motsvarar just att två textsekvenser landat på samma uppdaterade prompt utan fungerande radgräns. Det kan inte utifrån dessa data entydigt isoleras till `xdotool`-fördröjning, ett missat Enter, fokusförlust eller GUI-livscykel. Den enkla `sleep 2`-ändringen efter `run` i run 2 löste inte frågan; den gav ingen ny giltig `saveSes`.

**Gällande slutsats:** Fönstertitel, `xdotool` exit code och en `sleep` = **inte** kommandoack. Framtida ackkedja måste visa *mottagen rad, entydigt parsad respons, korrekt prompt och avskild transaktionsgräns*, en instruktion i taget.

## 3. FYND B – `saveSes` är en promptbuffertdump, ingen emulator-protokollkvittens

[`DebuggerParser::executeSaveSes` [2024–2058]](https://github.com/stella-emu/stella/blob/6.7.1/src/debugger/DebuggerParser.cxx#L2024-L2058) ger angivet filnamn till `debugger.prompt().saveBuffer` (utan filargument används userDir; med `?` öppnas GUI-file chooser). [`PromptWidget::saveBuffer` [931–958]](https://github.com/stella-emu/stella/blob/6.7.1/src/debugger/gui/PromptWidget.cxx#L931-L958) dumpar tidigare renderade teckenrader i intern **promptbuffert** fram till `_promptStartPos`, skriver fil och returnerar `saved ... OK` eller `unable to save session`. Detta är **inte** ett maskinläsbart kvitto på att varje `print` har blivit färdigbehandlat vid en speciell cykel och inte ens en oberoende logg utanför GUI:s prompttext.

I G5AL:s [`copy_session()` [149–158]](https://github.com/Odourman/let-me-out/blob/f16e1e4ac3736e3d6bb1bc0b959b0213e28f6431/rom/g5al_f9_method_2026-11-18/run_g5al_f9.sh#L149-L158) finns en verklig path, och tidigare lyckade `saveSes` visar att kommandot kan fungera i samma miljö. Run 2 saknar **en giltig nytillkommen fil efter `run`**. Källkod kan inte avgöra om kommandot aldrig nådde widgeten, om Return inte exekverades, om prompten inte var i fokus, eller om filskrivningen misslyckades. **Avsaknad av output-fil är verkligt FAIL men ger inte unik rotorsak**. Ett nytt `saveSes` med mer `sleep` ger ingen starkare transportgaranti.

## 4. FYND C – HÖGRISK: slutparsern läser FEL filnamn, och strict REENTRY-grindar är död kod

**C1 – deterministisk filnamnsinkonsekvens (STATIC BUG):** G5AL [runnerns `copy_session` rad 152](https://github.com/Odourman/let-me-out/blob/f16e1e4ac3736e3d6bb1bc0b959b0213e28f6431/rom/g5al_f9_method_2026-11-18/run_g5al_f9.sh#L149-L157) skapar `<STAGE>_debugger_session.txt`. Dess [`verify_session` rad 170–173](https://github.com/Odourman/let-me-out/blob/f16e1e4ac3736e3d6bb1bc0b959b0213e28f6431/rom/g5al_f9_method_2026-11-18/run_g5al_f9.sh#L170-L173) granskar **rätt** fil. Men [slutgranskarens `audit_g5al.py` rad 98–106](https://github.com/Odourman/let-me-out/blob/f16e1e4ac3736e3d6bb1bc0b959b0213e28f6431/rom/g5al_f9_method_2026-11-18/audit_g5al.py#L98-L106) öppnar **`<STAGE>_session.txt`**, alltså **en annan, icke-skapad fil**. Alla finala `stages` blir därför `MISSING` i en normal körning och [A/B/C kan inte bli samlat `PASS`](https://github.com/Odourman/let-me-out/blob/f16e1e4ac3736e3d6bb1bc0b959b0213e28f6431/rom/g5al_f9_method_2026-11-18/audit_g5al.py#L114-L132), **även om alla emulatorsteg senare fungerar**. Detta fel är oberoende av de faktiskt observerade run 1/run 2 hårdstopp.

**C2 – verifiering av rätt återinträdes-PC åsidosätts i `--gate` (STATIC BUG):** [`gate()` rad 44–55](https://github.com/Odourman/let-me-out/blob/f16e1e4ac3736e3d6bb1bc0b959b0213e28f6431/rom/g5al_f9_method_2026-11-18/audit_g5al.py#L44-L55) har **`if stage.endswith("HANDSHAKE")` före** `if stage=="A_REENTRY_HANDSHAKE"`/`"B_REENTRY_HANDSHAKE"`. De två specialgrindarna nås därför **aldrig**. Den generella regeln accepterar valfritt numeriskt PC och bank 0–3 om `Stella 6.7.1` finns i sessionen. En återinträdeshandshake med **fel PC** skulle därmed kunna klassas **PASS** av `--gate`. Detta innebär ett möjligt **falskt positivt** värde, medan C1 ger systematiska **falskt negativa** vid slutgranskning. Det är logiska källfakta, inte påståenden om att G5AL historiskt passerat A.

**Krav inför varje framtida ROM- eller instrumenteringsmätning:** En enda kanonisk sessionsfilnamnsfunktion för writer, `--gate` och final audit; en explicit **prioritetsordnad** `gate` där specifika återinträdesvillkor körs före generella handshake-villkor; separat **offline enhetstest** med positiva/negativa syntetiska sessioner och kontroller att både `--gate` och slutkörningen är konsekventa. Offline-parsergranskning är **INTE** Stella-runtime-/G5-metod-PASS.

## 5. Bedömning av mer deterministiska kontrollvägar

| Kandidat | Stöd från Stella 6.7.1 | Råbevismässig nytta/risk | Bedömning |
| --- | --- | --- | --- |
| Ännu längre `sleep` runt `xdotool` | Ingen applikationskvittens från kommandot; historisk run2 väntade längre utan session | Race och tyst inputförlust kvarstår | **AVRÅDS** som självständig metod |
| Händelsestyrd **transaktionskvittens** per GUI-kommando | Källan stöder separata text/Enter/resultat; `saveSes` kan exportera promptens historik | Kräver tydliga sekvensmarkörer, en kommandohändelse åt gången, faktisk eko/resultatkontroll; `saveSes` själv använder samma osäkra kanal | **Möjlig utan Stella-patch, EJ BEVISAD**; särskilt svårt när post-`run` prompten inte svarar |
| Skriptfil/`exec` (native batch) | [`DebuggerParser::exec` rad 135–163](https://github.com/stella-emu/stella/blob/6.7.1/src/debugger/DebuggerParser.cxx#L135-L163) läser filrad för rad och anropar `run(command)` | **Kritisk caveat:** `exec` **kastar bort retursträngen från varje `run(command)`**. `print`/registervärden får därför inte antas hamna som exporterade, maskinläsbara svar. `run` mitt i script kan dessutom lämna debugger medan scriptloop fortsätter | Möjlig för förregistrerad statisk setup; **INTE godkänd som runtime-svarsbevis** |

| Officiell terminal/TCP-API i omodifierad 6.7.1 | Ingen sådan maskinläsbar port observerad i kontrollerad `DebuggerParser`/`PromptWidget`/`Settings`/officiell användarmanual för detta scope | Avsaknad i undersökta delar bevisar **inte** att alla tänkbara externa mekanismer är omöjliga | **Ingen bekräftad färdig lösning** |
